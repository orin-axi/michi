### On the "operation contains `:`" question
This is a non-issue, and more strongly than "keys aren't parsed back apart" — even if someone *did* try to split a key back into `(operation, hash)`, it's still unambiguous. The hash segment is always exactly 16 lowercase hex characters (`0-9a-f`), which never contains `:`, and the format always appends exactly one `:` immediately before it. So the *last* 17 characters of any key are always `:` + 16 hex digits, regardless of how many colons appear inside `operation` itself. Two distinct `(operation, data)` pairs can only produce an identical key string via an actual 64-bit hash collision — never via colon placement ambiguity. I'd skip adding a doc caveat; the risk described doesn't actually exist, and the existing doc comment already covers the properties that do matter (determinism, non-cryptographic, `BTreeMap` ordering).
