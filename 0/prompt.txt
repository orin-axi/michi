### Issues

#### Critical (Must Fix)

**1. `Value` enum variants have no doc comments — violates the "every `pub` item has a doc comment" non-negotiable.**

`Value` is defined in `render.rs` and re-exported as a public type. All five variants (`Str`, `Int`, `Float`, `Bool`, `Null`) are public items with zero documentation. The plan's own Task 3 spec included variant-level comments:

```rust
/// UTF-8 string. Escaped if it contains commas, quotes, or newlines.
Str(String),
/// Signed integer.
Int(i64),
/// Floating-point number.
Float(f64),
/// Boolean renders as `true` or `false`.
Bool(bool),
/// Null renders as empty (delimiter still emitted).
Null,
```

These need to be added to `/Users/gabe/Projects/michi/src/toon/render.rs`.

---

#### Important (Should Fix)

**2. `# Panics` section on `render_toon` is semantically wrong.**

```rust
/// # Panics
///
/// Does not panic. Row lengths differing from `fields.len()` produce
/// misaligned output — caller's responsibility to match lengths.
```

The `# Panics` heading in Rust rustdoc convention means the function **can** panic under described conditions. A section that opens with "Does not panic" is misleading — a reader scanning docs for panic conditions will hit this and be confused. The misalignment note belongs either in the main description or under a custom `# Preconditions` heading. Remove the `# Panics` section entirely and fold the note into the description.

**3. No integration test for `Value::Float`.**

Every other `Value` variant is exercised at the integration level. `Float` is only reachable through the render path defined in `render.rs`, but there is no test that constructs a `ToonOptions` with a `Value::Float` and asserts the output. A floating-point rendering edge (e.g., `1.0` vs `1` vs `1.0000000000000002`) is worth a concrete assertion.

**4. Quote and newline escaping have no integration-level test.**

`escape_value` is unit-tested in `escape.rs`, but the integration suite tests only comma escaping (`escapes_comma_in_value`). There's no integration test that verifies a `Value::Str` containing `"` or `\n` produces correctly escaped TOON output. The risk is that a future refactor to `render.rs` breaks the `escape_value` call and the integration tests don't catch it.

---

#### Minor (Nice to Have)

**5. `render_toon` should carry `#[must_use]`.**

It returns a `String`. Silently discarding it is almost certainly a bug. `#[must_use = "discarding the rendered string has no effect"]` would make that a compile warning.

**6. `pub(crate) mod render` leaks a non-obvious API surface decision.**

`Value` is defined `pub` inside a `pub(crate)` module, then re-exported at the parent. This works correctly, but it means `render.rs`'s internal `pub fn render(...)` is callable from anywhere in the crate. Consider making `render` explicitly `pub(super)` if it's only intended for use by `mod.rs`. Low priority — but the current visibility is broader than necessary.
