## Architectural smells

**1. michi-core re-exports leaf crates wholesale, creating double-path access**
`michi-core/src/lib.rs:44-45`:
```rust
pub use michi_resilience::*;
pub use michi_truncate::*;
```
The root crate then does `pub use michi_core::*` AND `pub use michi_resilience as resilience`. This gives callers two identical paths to the same type: `michi::RetryConfig` (via core's glob) and `michi::resilience::RetryConfig` (via module alias). The core crate depends on michi-resilience only to re-export it — nothing in michi-core's own implementation calls any resilience function. This inverts the expected layering: michi-core should be the composition point for michi-toon, not a re-export conduit for orthogonal crates.

Fix: remove `pub use michi_resilience::*` and `pub use michi_truncate::*` from michi-core. Put those re-exports only in the root `michi/src/lib.rs` where they already exist as named module aliases.

**2. `help[N]:` format duplicated across a crate boundary**
`michi-resilience/src/lib.rs:306-315` and `michi-core/src/hints.rs:49-61` both write the exact same `help[N]:\n  hint\n` wire format. Since michi-resilience can't depend on michi-core, this duplication is forced by the current split. A format change requires two edits. This also means michi-resilience has an implicit contract with michi-core's output format that isn't expressed in code.

Fix: extract a `michi-format` (or `michi-wire`) leaf crate containing only the block-format writers (append_hints, append_recovery) with no other deps. Both michi-resilience and michi-core depend on it. Alternatively, move `render_already_done` into michi-core (it doesn't belong in resilience — it's a render function, not a retry primitive).

**3. `PartialSuccess::render()` writes `help[N]:` header manually inside michi-core**
`idempotency.rs:101-109`: even inside michi-core, idempotency bypasses `append_hints` and writes the `help[N]:\n` header by hand before calling `append_recovery_lines`. This is subtle: the body under `help[N]:` here is recovery-formatted lines, not hint strings — it's deliberately different from what `append_hints` would write — but writing the same header string in two places inside the same crate is fragile.

**4. `Pipeline` module is stranded — no composition seam into `AgentResponse`**
`pipeline/mod.rs`: `Pipeline::render()` produces TOON-like output, but `AgentResponse` has no `.pipeline()` builder method. A caller wanting to include pipeline state in a response must manually concatenate strings — they can't use the builder pattern. The module has data types and a renderer but no integration point.

## Extractable patterns

**5. `JsToonValue` is a dual-purpose type — the `decimals_val` field is the tell**
`napi.rs:40-63`: `JsToonValue` is used for both TOON row cells and KV values. The `decimals_val` field is documented "KV render only" — dead weight on a TOON value. Both `js_value_to_rust` and `js_kv_value_to_rust` take the same `JsToonValue` but produce different target types. The right fix is two types with two conversions:
```rust
// Split into:
From<JsToonValue> for michi_toon::Value   // no decimals_val
From<JsKvValue> for KvValue              // has decimals_val
```
`JsKvItem.value` would then be `JsKvValue` instead of `JsToonValue`, removing a footgun where a caller passes `decimals_val` on a TOON cell and it silently does nothing.

**6. `render_X` / `append_X` pattern in hints and recovery — consistent, not yet worth a trait**
`hints.rs:38-61` and `recovery.rs:38-82` both follow: `render_X` allocates and calls `append_X`; `append_X` does the actual work. This is a valid structural pair. It's NOT worth extracting into a trait yet — only two modules follow it as free functions, and others (DomainError, PartialSuccess, StatusResponse, Pipeline) use `fn render(&self) -> String` methods. If a third module needed the free-function pair, that's the extraction signal.

**7. Two independent `to_call_tool_result()` implementations with identical content-block logic**
`response.rs:206-222` and `error.rs:256-265`: `AgentResponse` and `DomainError` both produce `CallToolResult` through independent code. Both push an assistant content block, optionally a user block, and set `is_error`. A shared private helper in `michi-core::mcp`:
```rust
fn make_call_tool_result(
    assistant_text: String,
    user_text: Option<String>,
    is_error: bool,
    structured_content: String,
) -> CallToolResult
```
would ensure the two paths produce identically structured results as the format evolves.

## API gaps or traps

**8. No unified dispatch type between `AgentResponse` and `DomainError`**
`error.rs:256`: the doc comment on `DomainError::to_call_tool_result()` warns: "Do not wrap in `AgentResponse::as_error()` — that loses typed fields." This is a foot-gun: callers reading only the `AgentResponse` docs will reach for `as_error()` — it's the obvious path. There's no type that says "I contain either a success response or a typed domain error." A simple enum:
```rust
pub enum ToolOutput {
    Success(AgentResponse),
    Failure(DomainError),
}
impl ToolOutput {
    pub fn to_call_tool_result(&self) -> CallToolResult { ... }
}
```
would close this gap without breaking existing APIs.

**9. `TelemetryProvider` has no trait — real telemetry requires a breaking change**
`telemetry/mod.rs`: `NoopProvider` exposes `span()` and `count()` as concrete methods with no trait. A caller wanting to wire in OpenTelemetry or a metrics system has no contract to implement. The trait would be:
```rust
pub trait TelemetryProvider: Send + Sync {
    fn span(&self, name: &str);
    fn count(&self, name: &str, value: u64);
}
impl TelemetryProvider for NoopProvider { ... }
```
It should live in `michi-core/src/telemetry/`. Without this, any real telemetry integration requires a breaking API change.

**10. `KvValue` rendering is `pub(crate)` — external callers can't format a value**
`kv/mod.rs:34`: `push_kv_value` is `pub(crate)`. External crates holding a `KvValue` can only render it by going through `render_kv` with a full `KvItem`. If someone extends the status or recovery modules externally, they have no access to the value-render logic. The intentional reason for `pub(crate)` is the newline-stripping behavior in `KvValue::Text` — it's not a generic display. A separate `pub fn kv_value_display(v: &KvValue) -> String` (not `Display` — to avoid implying it's general-purpose) would give external callers access without misleading them.

**11. `render_toon()` / `render_kv()` vs `render(OutputFormat)` — two contracts on one builder**
`response.rs:168-181`: `render_toon()` and `render_kv()` are slot-specific (they always render their respective data slot regardless of which was set last). `render(OutputFormat::Text)` dispatches on `self.target`. A caller who calls `.kv_items()` then `.render_toon()` gets the TOON path with empty data — this is intentional per the tests, but the method names don't communicate the slot-specific contract. The distinction only makes sense in context of the NAPI layer needing to keep both slots live; for pure Rust callers, this is confusing API surface.

**12. `AgentResponse::as_error()` sets a bool, loses `ErrorCode` and typed fields**
`response.rs:116-119`: `.as_error()` only sets `is_error: true`. No error code, no recovery hint, no retryability. The `render_json()` output shape for an error response is `{"body":..., "isError":true, "hints":[], ...}` which differs from `DomainError::render_json()`'s shape `{"isError":true, "error":"not_found", "message":..., "retryable":..., ...}`. This means structured content consumers face two incompatible schemas depending on which path was taken. Finding 8 above (ToolOutput) is the right fix.

## Coherence issues

**13. `ToonOptions::hints: Vec<String>` vs `AgentResponse::hints: Vec<Hint>` — same data, different types**
`toon/lib.rs:85` vs `response.rs:39`: hints in ToonOptions are `Vec<String>`; in AgentResponse they're `Vec<Hint>`. `Hint` is a newtype over `String` (`hints.rs:5`: `pub struct Hint(pub String)`) with no validation or semantic enrichment — it's ceremony without safety. The NAPI layer converts `Vec<String>` → `ToonOptions.hints` directly; the Rust layer uses `Vec<Hint>`. `AgentResponse` then does NOT pass its hints through ToonOptions (it calls `finish_text` which calls `append_hints` separately). The `Hint` newtype should either be removed (just use `String` everywhere) or earn its keep by adding validation (non-empty, max length).

**14. `error.rs` does 5 jobs in one module**
`error.rs:1-306`: defines `ErrorClass` (classification), `Sensitive<T>` (wrapper), `ErrorCode` (variants + methods), `DomainError` (data type + builder + render + json + github annotation + mcp result), and `Error` (top-level enum). `Sensitive<T>` in particular has nothing to do with error classification — it's a general-purpose debug-redacting wrapper. `render_github_annotation()` is a formatter that knows about GitHub Actions format, which is far outside the scope of error classification. These could be split: data types in `error/types.rs`, rendering in `error/render.rs`, and `Sensitive<T>` moved to a top-level module or `michi-core/src/sensitive.rs`.

**15. `idempotency.rs` directly calls michi-toon escape functions for non-TOON output**
`idempotency.rs:82-85`: `PartialSuccess::render()` calls `michi_toon::escape_value()` and `michi_toon::escape_value_quoted()` to format the `failed[N]{operation,reason}:` block. This output looks like TOON but isn't — it's a custom block format that borrows TOON's cell-escaping rules. The coupling to michi-toon's escaping internals (`escape_value` is `pub` from michi-toon but conceptually an internal) means that if michi-toon changes its escaping semantics (e.g. adds a new structural char), PartialSuccess's output format would silently change too. The escape functions should either be documented as stable public contract, or PartialSuccess should duplicate the minimal escaping it needs.
