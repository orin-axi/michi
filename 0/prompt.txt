## HIGH IMPACT

### 1. `to_call_tool_result()` double-renders TOON and clones items twice
**`src/response.rs:206-222`**

`to_call_tool_result()` calls `self.render_text()` (line 207) and then `self.render(OutputFormat::Json)` (line 221). Both paths call `body()` → `toon_body()`. Each call to `toon_body()` clones `self.type_name`, `self.fields`, and `self.items` (the full `Vec<Vec<Value>>`), then builds a ToonOptions, validates it, and renders it.

```rust
fn toon_body(&self) -> String {
    let opts = michi_toon::ToonOptions::new(
        self.type_name.clone(),   // clone
        self.fields.clone(),      // clone  
        self.items.clone()        // clone — potentially thousands of rows × N fields
    )
    ...
}
```

For a response with 1000 rows × 5 fields, this is 5000 `CompactString` clones happening twice. The rendered TOON string is also built twice, then the first copy is JSON-embedded in `render_json`. Fix: compute the TOON body once, reuse for both ContentBlock text and JSON `"body"` field.

### 2. `toon_body()` clones the full items Vec on every render call
**`src/response.rs:130`**

Same structural issue as above: every `AgentResponse::render_text()`, `render_toon()`, and `render_kv()` + hints path that goes through `body()` clones the entire data. The `ToonOptions::new()` API requires owned data, forcing this. The `render::render()` function in michi-toon only needs references — the clone is an artifact of the builder taking ownership. This could be fixed by making `render::render` accept borrowed data (it already takes `&[String]` for fields and `&[Vec<Value>]` for rows, so `toon_body` just needs to pass references rather than clone-then-pass).

Actually looking again at `render::render` signature:
```rust
pub(crate) fn render(type_name: &str, fields: &[String], rows: &[Vec<Value>], ...) -> String
```
It already takes references. The problem is `ToonOptions::new()` takes `Vec<Vec<Value>>` owned. `toon_body` creates a `ToonOptions` just to validate and call `render_toon`, but `render_toon` in turn calls `render::render` with references. So the clone is wasted: `toon_body` could call `render::render` directly with `&self.type_name`, `&self.fields`, `&self.items` and skip ToonOptions entirely — or expose a `render_toon_ref` path.

### 3. `truncate_inline` allocates even when no truncation occurs
**`crates/michi-truncate/src/lib.rs:92-94` and `crates/michi-toon/src/render.rs:174-179`**

In `render.rs`, the truncation guard is a byte-length check:
```rust
if s.len() <= max_cell_len {
    out.push_str(&escape_value(s));        // fast path, no alloc
} else {
    let truncated = michi_truncate::truncate_inline(s, max_cell_len, "full=true");
    out.push_str(&escape_value(&truncated));  // always allocates
}
```

When a string has byte length > 200 but char count ≤ 200 (e.g., multibyte UTF-8), `truncate_inline` is invoked unnecessarily. Inside `truncate`, it detects no truncation is needed and returns early — but still as `content.to_string()`, a heap allocation. `truncate_inline` should return `Cow<'_, str>` so the no-op case returns `Cow::Borrowed(content)` without copying.

## MEDIUM IMPACT

### 4. `to_string()` on integers/counts allocates temporary Strings in the hot path
Multiple locations in string-building code use `x.to_string()` where `write!(out, "{x}")` would write directly to the existing buffer:

- `crates/michi-toon/src/render.rs:155`: `out.push_str(&row_count.to_string())`
- `crates/michi-toon/src/render.rs:205`: `out.push_str(&total.to_string())`
- `crates/michi-toon/src/render.rs:210`: `out.push_str(&hints.len().to_string())`
- `crates/michi-core/src/hints.rs:54`: `out.push_str(&hints.len().to_string())`
- `crates/michi-core/src/recovery.rs:55`: `out.push_str(&hints.len().to_string())`
- `crates/michi-resilience/src/lib.rs:308`: `out.push_str(&hints.len().to_string())`

Each is a heap allocation (typically 1-3 bytes of content) on every render call. With `write!(out, "{x}")` these write directly into the pre-allocated buffer with no intermediate String.

### 5. `render_for(Audience::User)` clones the human_content String on every call
**`src/response.rs:194`**

```rust
crate::audience::Audience::User => self.human_content.clone().unwrap_or_else(|| self.render_text()),
```

`clone()` on the `Option<String>` forces a heap copy of the human content string on every `render_for(User)` call. Since `render_for` returns an owned String anyway, this can't be fully eliminated without API changes, but the pattern could return `Cow<'_, str>` to avoid the copy in the common single-call case.

### 6. `KvValue::Duration` in `kv_value_to_json` creates an intermediate String
**`crates/michi-core/src/kv/mod.rs:101-103`**

```rust
KvValue::Duration(d) => {
    let mut secs = String::new();
    let _ = write!(secs, "{:.1}s", d.as_secs_f64());
    json_escape_str(out, &secs);
}
```

`json_escape_str` then wraps in quotes and escapes special chars — but a duration string like `"1.5s"` is pure ASCII with no escapable chars. The intermediate `secs` String is unnecessary. Could write directly: `out.push('"'); let _ = write!(out, "{:.1}s", d.as_secs_f64()); out.push('"');`.

Same pattern for `KvValue::Float` NaN/Inf in the JSON path (`kv/mod.rs:93-95`): `let s = format!(...)` then `json_escape_str(out, &s)` — the formatted float string contains no escapable characters.

## LOW IMPACT

### 7. `sanitize_header_token` double-scans in the mutation path
**`crates/michi-toon/src/escape.rs:78-79`**

```rust
if s.chars().any(|c| STRUCTURAL.contains(&c)) {
    std::borrow::Cow::Owned(s.chars().map(|c| if STRUCTURAL.contains(&c) { '_' } else { c }).collect())
} else {
    std::borrow::Cow::Borrowed(s)
}
```

When structural chars are found, this scans the string twice (once with `any`, once with `map`). Could do it in one pass. For the common unescaped case (borrowed path), this is a non-issue. For the mutation path, could combine into a single `map().collect()` and check dirty flag. `STRUCTURAL.contains(&c)` is also a linear scan of a 7-element slice — a small byte lookup table would be faster, but at 7 elements this is negligible.

### 8. `render_kv` calls `.chars().count()` twice per key
**`crates/michi-core/src/kv/mod.rs:120,126`**

```rust
let max_key_len = items.iter().map(|i| i.key.chars().count()).max().unwrap_or(0);
// ...
for item in items {
    // ...
    let pad = max_key_len - item.key.chars().count() + 1;  // recomputes for each item
```

`chars().count()` is O(len) for UTF-8 strings. For all-ASCII keys (the common case for field names), this is fast, but it runs 2N times. A precomputed `key_lengths: Vec<usize>` or a single-pass struct would eliminate the recomputation. For typical small KV sets (< 20 items), the savings are minimal.

### 9. Capacity estimate in `render` may cause reallocs for large string cells
**`crates/michi-toon/src/render.rs:149`**

```rust
let capacity = 60 + row_count * (field_count * 12 + 10) + hints.len() * 60;
```

The 12-byte-per-cell estimate is a rough guess. For rows where string cells are frequently near the `max_cell_len` (200 chars default), actual output will be ~16× larger than estimated, causing multiple reallocs. The `total_count` line and header line are also not included in the estimate. Not catastrophic but worth noting for workloads with large string cells.

### 10. `miette` feature allocates a `Vec<&str>` for the hints display
**`crates/michi-core/src/error.rs:285-288`**

```rust
Some(Box::new(self.hints.iter().map(|h| h.as_str()).collect::<Vec<_>>().join("\n")))
```

Allocates a Vec of `&str` just to join them. Could use itertools or a custom Display impl. This is only in the `miette` feature, which is optional and not in the hot path.

## Feature Flag Impact

The `serde` feature adds `Serialize/Deserialize` derives to `Value`, `KvValue`, `ContentBlock`, etc. These add zero runtime overhead to the rendering hot paths — no serde code runs during `render_toon` or `render_kv`. The only serde overhead is in the `list()` convenience function, which calls `serde_json::to_value()` per item (full serialization to a JSON value tree), then extracts fields from a `BTreeMap`. This is expensive relative to building `ToonOptions` directly, but `list()` is a convenience wrapper, not the primary API.

## Quickest Wins (highest ROI, lowest risk)

**1. Replace all `x.to_string()` → `write!(out, "{x}")` in buffer-building code**
Six locations. Each eliminates one heap allocation per render call. Purely mechanical, zero risk. Combined saves ~6 small allocs per `render_toon` call.

**2. Fix the double-render in `to_call_tool_result()`**
Compute the TOON/KV body string once, use it for both the ContentBlock text and the JSON `"body"` field. Halves the number of full renders (and the associated clones) in the most common MCP call path. Medium effort, high-value.

**3. Make `toon_body()` call `render::render` directly instead of via ToonOptions**
`render::render` already takes references. `toon_body()` clones three fields just to construct a `ToonOptions` that is immediately passed to `render_toon()` which immediately unpacks it back into references. Bypassing `ToonOptions` construction in this internal path eliminates the clones entirely.

**4. Return `Cow<'_, str>` from `truncate_inline`**
For the no-truncation case (common), avoids a heap copy. Requires changing the function signature from `-> String` to `-> Cow<'_, str>`. The caller in `render.rs` already uses `&escape_value(&truncated)` which would need adjustment, but `escape_value` already returns `Cow<'_, str>` so the chain composes naturally.

**5. Add benchmarks for the missing paths**
Without benchmarks for `to_call_tool_result`, `render_kv`, and the truncation path, there is no way to measure whether fixes in findings 1-3 actually move the needle. The benchmark suite needs these before any optimization work is verifiable.
