### Code Quality Issues

**Low — cosmetic**

`render_hints` does `out.push_str(&amp;hints.len().to_string())` which allocates a temporary `String` for the count. `write!(out, "{}", hints.len())` or splitting into a `format!` for the whole header line would avoid the allocation. Not a correctness issue; the heuristic `with_capacity` estimate already over-allocates anyway.

**Low — semantic ambiguity in doc comment**

`Truncated::original_len` is documented as "Original **byte** length of the input" and stores `content.len()` (bytes). The entire API is char-count-based (`max_chars`, suffix counts, cap guard). A caller who wants to know "how many chars were in the original" has to call `.chars().count()` separately. The field isn't wrong, but naming it `original_len` while the rest of the API thinks in chars is a mild mismatch. No spec violation — the spec only names the field, not its semantics — but worth flagging for future readers.

**None — hard-cap guard** is a sound addition, not a quality concern.
