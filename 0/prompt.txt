# Edge-Case Audit: `toon` + `truncate`

Read completely: `crates/michi-toon/src/{lib,render,escape,serializer}.rs`, `crates/michi-truncate/src/lib.rs`, `docs/spec/02-toon-format.md`, `docs/spec/03-rust-api.md`, `tests/{toon_integration,toon_parser,proptest_toon,proptest_truncate}.rs`, `tests/support/toon_parser.rs`, `tests/snapshot_tests.rs` (toon parts), `benches/toon_render.rs`.

## escape.rs

**(a) Handled + tested**
- Comma → quoted (`value_with_comma_is_quoted`)
- Quote → escaped `\"`, whole value quoted (`value_with_quote_escapes_it`)
- Empty string → unchanged, no allocation (`empty_value_is_unchanged`)
- Plain value → `Cow::Borrowed`, no copy (`plain_value_is_not_escaped`)
- `\n`/`\r` stripped silently (integration: `newline_in_value_is_stripped`; proptest: round-trip normalizes by stripping)
- Round-trip grammar validity across random comma/quote/CR/LF mixes (proptest_toon, `cell_strategy`)

**(b) Handled in code, NOT tested**
- `escape_value_quoted` (unconditional-quote variant) — zero direct tests anywhere, not even a unit test in escape.rs, and no caller found in render.rs. Reachable only via public re-export; if meant for a specific caller (e.g. `kv` module), that caller isn't exercised here either.
- A value containing only `\n`/`\r` and nothing else that needs quoting (e.g. `"a\nb"`, no comma/quote) — takes `needs_quote=false`/`stripped_count>0` path, unquoted + stripped. Correct per spec but only covered incidentally via proptest, no dedicated unit test.
- Value that's only a quote char (`"\""`) — renders `"\""`. Not directly asserted.

**(c) Gaps / not handled**
- **No quoting for ambiguous-looking scalars.** Grammar (`docs/spec/02-toon-format.md:21`) allows any string minus `,\n"` unquoted, so a string value `"true"`, `"42"`, or empty-string vs. null are unquoted and grammar-indistinguishable from bool/int/absent. Not a bug in `escape_value` (matches documented grammar), but nothing tests/documents this ambiguity; a round-tripping consumer would silently misinterpret e.g. string `"42"` as a number.
- **No validation of `type_name` / `field_name`.** `render()` writes these raw into the header (render.rs:150-159) with zero escaping. Grammar requires `[a-z_][a-z0-9_]*`. A field name containing `,`/`{`/`}`/`:`/newline silently corrupts the header (e.g. splits into extra fields). No code enforces this, no test exercises it. Given `ToonOptions` fields are `pub`, any caller can trigger silent corruption — comparable in spirit to the existing row/field-count `debug_assert!`, but this one has no guard at all, debug or release.

## render.rs

**(a) Handled + tested**
- Basic row/field/count rendering, multi-row; empty rows+fields (`issue[0]{}:`); total_count presence/absence; hints block singular/multiple; `Value::Null`→empty cell; `Value::Bool`→true/false; mixed numeric rows incl. negatives/floats; per-cell truncation via `max_cell_len` with escaping applied post-truncation; short strings untouched.

**(b) Handled in code, NOT tested**
- **Row/field-count mismatch `debug_assert!`** (render.rs:139-143) — no test triggers it, and it's compiled out in release builds. A mismatched row (e.g. 2 values against a 3-field header) silently misaligns output with **zero runtime protection in release**. Since `packages/michi-node` ships a release NAPI binary, this is reachable in production if a Node caller supplies mismatched arrays — silent wrong output, no panic, no signal. This is the most concrete correctness gap found in render.rs.
- `max_cell_len == 0` — falls through to `michi_truncate::truncate_inline` which has its own guards, likely safe, but zero test coverage at this boundary at the toon layer specifically.
- `Value::Float` special values: `NAN`/`INFINITY`/`-INFINITY` render as `NaN`/`inf`/`-inf` via Rust `Display` — not valid TOON numeric scalars per grammar, zero test coverage.
- Very large row/field counts beyond bench's 1000 rows / proptest's 0..5 rows — no correctness test at scale, only perf bench.

**(c) Not handled**
- **`hints` bypass all escaping.** `render()` writes each hint directly (render.rs:205: `out.push_str(hint)`) with no stripping/escaping, unlike cell values. A hint containing `\n` injects an unprefixed extra line into the `help[N]:` block, silently breaking the declared count vs. actual line count. No test covers a hint with embedded `\n`.
- Same issue for `type_name` and field names containing `\n` — corrupts the header line, no escaping applied anywhere in the header-writing path.
- These two (header + hints unescaped) are the **highest-value gap** in the whole audit: most reachable from realistic inputs (dynamic type/field names, agent-composed hint text) and produces corrupt, unparseable output with no error anywhere in the pipeline.

## serializer.rs / toon::list()

- `toon::list()` in lib.rs actually round-trips through `serde_json::to_value(item)` + hand-written `json_value_to_toon_value`, **not** through `serializer.rs`'s `ValueSerializer`. The module doc-comment on serializer.rs claims it exists "to stream... without intermediate `serde_json::Value` allocations" — that claim appears **false for the only public entry point**. `ValueSerializer`/`ToonSerError` and all their error paths (`serialize_seq`/`tuple`/`map`/`struct` all `Err`) have zero test coverage and may be entirely dead code reachable from nothing. Worth a quick grep for other call sites before assuming so; if unused, either wire it in or remove it — currently doc/implementation drift.
- `list()`'s `match serde_json::to_value(item) { Ok(Object(map)) => map, _ => Map::new() }` silently treats any non-struct item (bare array, string, number) as an **empty row** — no test covers `toon::list("t", &[1,2,3])`; this is silent data loss with no signal.
- `u64` values near `u64::MAX` are clamped to `i64::MAX` (both in `json_value_to_toon_value`'s numeric fallback and `ValueSerializer::serialize_u64`) — untested at either layer; silently wrong for large hash-derived IDs.
- `serialize_bytes` → `format!("{v:?}")` produces a comma-containing string (`[1, 2, 3]`) — untested end-to-end through `escape_value`.

## truncate.rs (michi-truncate)

**(a) Handled + tested** — thorough: short/exact-length untouched, long truncated with correct char-count signal, CJK/multibyte char-boundary safety, `truncate_inline` wrapper, signal presence/absence, byte-length fast path for large-but-under-limit content, proptests for length bound and UTF-8 validity across limit 1..100 / content 0..500.

**(b) Handled in code, NOT tested — includes one likely real bug**
- **`signal` vs `content` divergence at small `max_chars`.** Line 74's `signal: Some(suffix.trim_start().to_string())` uses the **original uncapped** `suffix` string, while `content` may have been hard-capped (lines 65-68) to something much shorter. At very small `max_chars` (e.g. 1-10 with the ~30-char `"full=true"` hint text), `content` becomes near-garbage (e.g. a single `"("` or space) while `signal` still reports the full, untruncated explanatory text. These two fields can diverge in a way that's surprising to any caller treating `signal` as "the text embedded in content." Not documented, not tested, plausible real bug depending on how `signal` is consumed elsewhere (outside this audit's scope — worth a follow-up grep in `kv`/`response` modules).
- Related: **hard-capped suffix produces unreadable/uninformative content** at very small `max_chars` — `was_truncated: true` but the visible signal text is chopped mid-word, communicating nothing useful. Proptest (`limit in 1..100`) exercises this path without panicking but never asserts on *readability/usefulness*, only on length bound.

No test covers non-trivial hint values.
- Multibyte content that's short in **chars** but long in **bytes** (e.g., a string of few-but-4-byte emoji vs. `max_chars=10`) — only fast-path branch (`content.len() <= max_chars`) is clearly covered by ASCII tests; the second fast path (`char_count <= max_chars` when byte len > max_chars) is only indirectly touched by the CJK test, which likely exceeds both limits anyway. Real coverage gap for "not truncated, but only detectable via full char scan."
