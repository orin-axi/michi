### API design assessment: `KvValue::Float(f64, u8)`
Reasonable, not awkward in practice. Every current call site (tests, `duration_renders_as_seconds_with_one_decimal`-style usage) constructs `Float` with an explicit precision inline (`Float(1.0/3.0, 2)`), so it reads naturally as "value + how many decimals to show," similar to how `{:.2}` reads in a format string — it's not fighting the call sites. The alternative (a separate rendering-option struct or a `render_kv` parameter for global float precision) would be worse: precision is inherently per-value semantics (a `ratio` field wants 2 decimals, a `price` field might want 2, a `confidence` might want 3), so baking it into the enum variant is the right call over threading a global option through the renderer. Only mild wrinkle is the cross-module inconsistency noted above (`recovery.rs` ignoring the `u8`), which is a call-site bug, not evidence the API shape itself is wrong.
