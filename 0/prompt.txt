## (c) Edge cases NOT handled at all (gaps/bugs)

1. **[Real bug, medium severity] Invalid calendar dates in HTTP-date silently accepted instead of rejected.** `parse_http_date` validates `day` in `1..=31` and time ranges, but never checks `day` against actual days-in-month/leap-year-ness. `days_from_civil` is pure arithmetic (Howard Hinnant algorithm) with no calendar validity check. E.g. `"Wed, 30 Feb 2026 07:28:00 GMT"` does NOT return `None` — it silently parses as March 2, 2026. This contradicts the spec's stated contract ("Returns `None` for anything malformed", `06-decisions.md:258`): a malformed-but-plausible date from a buggy/malicious upstream produces a wrong `Duration` instead of falling back to backoff-only.
2. **[Behavioral trap, low-medium severity] `max_delay = 0` silently discards an explicit server `retry_after`.** `capped_ms = jittered_ms.max(retry_after_ms).min(max_ms)` — if `max_ms==0`, the final `.min(0)` zeroes out even an explicit "wait 60s" from the server, causing immediate retry against a server's explicit backoff request. No config validation prevents `max_delay=0` or `base_delay > max_delay`.
3. **[Low severity, documentation gap] No `RetryConfig` field validation.** `jitter_factor` is documented as `[0.0, 1.0]` (lib.rs:21-22) but unenforced. Negative values get silently floored to 0 via Rust's saturating float->u64 cast (no panic, but silent misbehavior); values >1.0 are only rescued by `.min(max_ms)`, not by any documented behavior.
4. **[Low severity, interop gap] RFC 7231 obs-date formats (RFC 850, asctime) unsupported**, and this isn't documented as a known limitation anywhere in the spec's format table. Verified safe by inspection — both alternate formats fail to tokenize and correctly fall through to `None` (no misparse), just unstated non-support relative to RFC 7231 §7.1.1.1's recipient guidance.
5. **[Low severity] Oversized delta-seconds silently degrades to "ignore the header."** A `Retry-After` value like `"99999999999999999999999"` overflows `u64::parse`, falls through to HTTP-date parsing, fails, returns `None` — indistinguishable from garbage input, rather than saturating to a large duration.
6. **[Very low severity] No weekday/date cross-validation** — `_weekday` in HTTP-date is parsed and discarded without checking consistency against the computed day-of-week. Combined with gap #1, there's no cross-field consistency check anywhere in the date format.
7. **[Doc bug] Spec/code naming mismatch**: `06-decisions.md:259` references `config.initial_delay` as the floor `next_retry_delay()` clamps to, but the actual field is `base_delay` (lib.rs:18) — `initial_delay` doesn't exist in code anywhere. Worth fixing since it's the exact clause explaining the past-date-safety guarantee.
