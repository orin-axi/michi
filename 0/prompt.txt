### Issues

#### Important (Should Fix)

**1. `render()` signature diverges from the plan — Task 3 friction**

The plan specifies:
```rust
pub(crate) fn render(opts: &amp;ToonOptions) -&gt; String
```
The implementation uses:
```rust
pub(crate) fn render(type_name: &amp;str, fields: &amp;[String], rows: &amp;[Vec&lt;Value&gt;], total_count: Option&lt;usize&gt;, hints: &amp;[String]) -&gt; String
```
Task 3 plans to call `render::render(opts)`. With the current flat signature, Task 3 cannot follow its plan verbatim and must either modify this function's signature or adapt its call site. Both files are internal, so this is recoverable — but it is avoidable churn that will need a conscious decision at the start of Task 3.

**2. `\r` (carriage return) not handled — live data risk**

Verified with concrete execution: `"line\rend"` passes through `escape_value` unquoted. The `\r` is not caught by `contains('\n')`. If TOON field values originate from HTTP responses, file uploads, or Windows-style text (where `\r\n` is the line terminator), a trailing `\r` in a field will be emitted before the newline the render function appends — producing a `\r\n` line ending in TOON output that may cause parsing failures downstream.

Fix: add `|| v.contains('\r')` to the condition on line 10 of `escape.rs`, plus a corresponding test `value_with_cr_is_quoted`.

**3. `with_capacity` underestimates for quote-heavy strings**

Verified with concrete execution: a 6-char string of all double-quotes gets `capacity = 8` but produces 14-char output, requiring reallocation. The `+2` only accounts for the surrounding quotes; each embedded `"` needs an extra `\` escape byte that isn't budgeted.

The simplest fix without a second scan pass is to use `v.len() * 2 + 2` as the worst-case estimate (every char is a `"`). The more precise fix — `v.len() + 2 + v.bytes().filter(|&amp;b| b == b'"').count()` — is exact at the cost of one pre-scan. Either is preferable to silent reallocation in the slow path.
