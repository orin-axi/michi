**(a) What codegraph actually is (commit `ea72e1b`, cloned to `/tmp/codegraph-research`).** It's a TypeScript project (341 `.ts` files) with a native Rust extraction kernel (`codegraph-kernel/`, NAPI v3, tree-sitter parsing only — 26 `.rs` files, nothing to do with response formatting). Agent-facing access is a **completely hand-rolled MCP server**: `src/mcp/transport.ts` implements newline-delimited JSON-RPC 2.0 from scratch (`StdioTransport`/`SocketTransport`, ~330 lines), `src/mcp/session.ts` handles `initialize`/`tools/list`/`tools/call`, and there is **zero dependency on `@modelcontextprotocol/sdk`** — `package.json` has no such dependency, and the only occurrence of the string `modelcontextprotocol` in `src/` is a spec-URL comment (`src/mcp/tools.ts:468`). Tool output is `ToolResult { content: [{type:'text', text}], isError? }` (`src/mcp/tools.ts:493-499`), built by two trivial helpers `textResult`/`errorResult` (`tools.ts:4698-4709`). Every tool response is **hand-authored Markdown prose**, never JSON — dedicated formatters like `formatSearchResults`, `formatNodeList`, `formatImpact`, `formatNodeDetails` (`tools.ts:4571-4696`) build `**bold headers**`, bullet lists (`- name (kind) - path:line`), and code fences directly.

**(b) Verdict: weak-to-no genuine fit**, evidenced, not just architectural mismatch.

- **TOON**: doesn't apply. codegraph never serializes JSON to the agent to begin with — it bypassed the "repeated JSON field names" problem TOON solves by hand-writing compact positional text (`- ${node.name} (${node.kind}) - ${node.filePath}${location}`) directly, and that helper (`formatNodeList`) is already shared across callers/callees, so there's no duplicated list-rendering logic to consolidate either.
- **AgentResponse builder**: no fit — each tool's output is bespoke prose (structural outlines, blast-radius summaries, config-key redaction notices), not a generic entity list/kv shape.
- **Diagnostic-style per-item degraded signal**: absent entirely. Grepped `src/` for `Diagnostic`/`diagnostic` — only log/comment hits, no struct. Per-file failure (e.g. "could not read from disk", `tools.ts:3945`) is handled ad hoc, inline, per call site — no repeated pattern analogous to monokl's 21x `diagnostics: Vec&lt;Diagnostic&gt;`.
- **mcp module**: no fit, and by design — michi's own `src/mcp.rs` doc comment explicitly disclaims "JSON-RPC, tool registration, server bootstrapping" as non-goals. That's precisely the layer codegraph hand-rolls (transport.ts, session.ts) — michi wouldn't touch it. The only part michi's mcp module *could* replace is the already-minimal 12-line `textResult`/`errorResult`, and codegraph deliberately never populates `structuredContent` or per-block `audience` annotations (grepped — zero hits), so adopting michi's `CallToolResult{content, isError, structuredContent}` shape would be adding a capability codegraph doesn't use, not eliminating duplication.
- **truncate**: the closest thing to a real match, but weak. codegraph's `truncateOutput` (`tools.ts:4559-4565`, `text.slice(0,15000)` + last-newline cut + fixed suffix) is called from ~13 sites — already centralized in one function, not duplicated. It's real but there's a separate, far more sophisticated budget/truncation system for `codegraph_explore` (`tools.ts:3682-3728`) that cuts on file-section boundaries, tracks "Not shown above" survivor lists, and reports exact symbol/file counts — domain logic no generic char-truncator (including michi's) can replace.

**Bottom line**: codegraph is 100% TypeScript at the agent-response layer; its only Rust surface (`codegraph-kernel`) is parsing, architecturally sealed off from formatting.
