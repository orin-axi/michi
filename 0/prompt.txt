## Research Report: 2026 Publishing Best Practices for a Rust + napi-rs Two-Package Release

### 1. crates.io Publishing (2026)

**Required metadata:** `cargo publish` rejects packages missing `description`, `license` (or `license-file`), and `repository` in `Cargo.toml`. A `readme` field (or an auto-detected `README.md`/`README.txt`/`README`) is uploaded as the crate's source-of-truth and rendered as Markdown on the crate page. ([Cargo Book — Publishing](https://doc.rust-lang.org/cargo/reference/publishing.html), [Manifest Format](https://doc.rust-lang.org/cargo/reference/manifest.html))

**Trusted Publishing is GA and the recommended default.** crates.io shipped OIDC-based Trusted Publishing with full rollout in **July 2025** (RFC 3691), and it has continued to mature through 2026: GitLab.com support was added, crate owners can now flip on **"Trusted Publishing Only" mode** (disables classic API tokens entirely for that crate), and risky trigger types (`pull_request_target`, `workflow_run`) were blocked from use with it after abuse incidents. Mechanically: your GitHub Actions workflow requests an OIDC token, `rust-lang/crates-io-auth-action` exchanges it for a short-lived (~15–30 min) publish token, and `cargo publish` uses that — no `CARGO_REGISTRY_TOKEN` secret stored anywhere. This is now the recommended approach over long-lived API tokens for CI-based publishing. Adoption is real but still a minority (~770+ crates as of mid-2025, including `pyo3`, `cc`). Sources: [crates.io docs — Trusted Publishing](https://crates.io/docs/trusted-publishing), [RFC 3691](https://rust-lang.github.io/rfcs/3691-trusted-publishing-cratesio.html), [crates.io Jan 2026 dev update](https://blog.rust-lang.org/2026/01/21/crates-io-development-update), [Simon Willison write-up](https://simonwillison.net/2025/Jul/12/cratesio-trusted-publishing/).

**Release automation:** `release-plz` (version bump PRs, changelog generation via git-cliff, and crates.io publishing — supports Trusted Publishing) is the standard tool for pure-library crate releases. `cargo-dist` (still actively maintained by axodotdev, releases ongoing into mid-2026) is the standard for shipping *binaries/GitHub Releases* across platforms, not crates.io publishing per se. The common combined pattern: **release-plz** for version/changelog/crates.io publish, **cargo-dist** for building/distributing binaries, used together rather than as competitors. Sources: [release-plz.dev](https://release-plz.dev/), [Orhun's automated-rust-releases](https://blog.orhun.dev/automated-rust-releases/), [cargo-dist GitHub](https://github.com/axodotdev/cargo-dist).

Not directly verified but worth flagging: whether release-plz's crates.io publish step is fully compatible with Trusted-Publishing-Only mode (vs needing a token) wasn't confirmed in sources — check release-plz's own docs before enabling enforcement mode.

### 2. npm Publishing for napi-rs Multi-Platform Packages (2026)

**napi-rs's own scaffolded pattern is the standard, and it is optionalDependencies-based, not postinstall-download-based.** A root package (e.g. `@orin-axi/michi`) depends on per-target platform packages (e.g. `@orin-axi/michi-darwin-arm64`, `@orin-axi/michi-linux-x64-gnu`) declared as `optionalDependencies`; each platform package's `os`/`cpu`/`libc` fields let npm/yarn/pnpm auto-select the right binary at install time — no postinstall script, no runtime download. This is also the pattern used by SWC and Rolldown, i.e. it's the ecosystem-wide convention for native Node addons via napi-rs, not just napi-rs's own preference. The napi-rs CLI scaffolds this directly: `napi create-npm-dirs` → `napi build` (per-target, matrix CI) → `napi artifacts` → `napi pre-publish` (syncs versions, publishes platform packages) → `npm publish` (root package). Sources: [napi.rs — Release native packages](https://napi.rs/docs/deep-dive/release), [napi.rs — Getting started](https://napi.rs/docs/introduction/getting-started).

**npm Trusted Publishing is GA (as of July 31, 2025)** and napi-rs's generated CI explicitly supports it — its docs instruct keeping `id-token: write` on the publish job for provenance/trusted publishing. Requirements: npm CLI ≥ 11.5.1, Node ≥ 22.14.0, GitHub-hosted runners only (self-hosted unsupported), and the registered workflow filename + repo must match exactly what's configured on npmjs.com. Once trusted publishing is set up, provenance attestation is generated automatically (the `--provenance` flag is no longer needed). One 2026 wrinkle: **trusted-publisher configs created after May 20, 2026 must explicitly select which actions (publish / stage publish) are allowed** — older configs default to "publish only" with no behavior change. Sources: [GitHub Changelog — npm trusted publishing GA](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/), [npm docs — Trusted publishers](https://docs.npmjs.com/trusted-publishers/), [philna.sh — npm trusted publishing gotchas, Jan 2026](https://philna.sh/blog/2026/01/28/trusted-publishing-npm/).

**Multi-package caveat (unsettled/under-documented):** npm's trusted-publishing docs describe a single package/single workflow model. They do not explicitly address publishing *several* packages (root + N platform packages) from one workflow run, which is exactly michi-node's shape. In practice each package name would need its own trusted-publisher registration on npmjs.com pointing at the same workflow file, and it's worth verifying in napi-rs's actual CI template (not just its prose docs) how it sequences multiple `npm publish` calls under a single OIDC-token-granting job — this is the part of the picture that's least explicitly confirmed by primary sources and should be validated hands-on before relying on it.

### 3. SemVer / First-Release Versioning

Standard Rust-ecosystem convention is **start at 0.1.0**, even for an API the author considers stable — this is described as the de-facto norm, and Cargo's semver interpretation for 0.x crates is intentionally different from strict SemVer (a 0.1→0.2 bump is treated as breaking; 0.1.0→0.1.1 can add features). Going straight to 1.0.0 is explicitly endorsed as *not* something to be afraid of once you're genuinely committing to API stability — some commentary calls out that crates that stay on 0.x forever squander SemVer's expressivity (losing the major/minor/patch distinction down to just "breaking/not"). The practical objection to jumping straight to 1.0.0 for a first-ever release is that it's hard to know your breaking-change cycle is truly over the first time. There's no crates.io/npm registry-level penalty either way — this is a social/API-stability signal, not an enforced mechanism, and reasonable engineers disagree here; treat "0.1.0 is more standard for a *first* release" as the default recommendation but recognize going 1.0.0 is legitimate if you're confident. Sources: [Rust Project Primer — Versioning](https://rustprojectprimer.com/releasing/versioning.html), [Effective Rust — semver](https://lurklurk.org/effective-rust/semver.html).

### 4. CHANGELOG Conventions

**Keep a Changelog format + Conventional Commits + automated generation is still the standard combo in 2026** — nothing has superseded it. `git-cliff` (Rust-native, actively maintained, v2.13.x as of mid-2026) is the standard generator: it parses Conventional Commits and emits Keep-a-Changelog-formatted output, and is what `release-plz` uses under the hood for changelog automation as part of its release-PR workflow. No credible alternative paradigm displacing this combo showed up in 2026 sources. Sources: [git-cliff.org](https://git-cliff.org/), [release-plz.dev](https://release-plz.dev/), [slhck.info — migrating to git-cliff, Oct 2025](https://slhck.info/software/2025/10/13/git-cliff-for-changelogs.html).

### 5. AGPL-3.0 Licensing Friction

**SPDX identifier correctness matters and is a known historical pain point.** Registries expect the current SPDX identifiers `AGPL-3.0-only` or `AGPL-3.0-or-later` — the bare `AGPL-3.0` string is a **deprecated SPDX identifier** and using it can cause security/compliance tools (e.g., Snyk) to flag the package incorrectly. There's a long-standing (2018-era) crates.io GitHub issue where `AGPL-3.0-or-later` was rejected as "unknown license" — I could not confirm from available sources whether/when that specific bug was fixed, so **this is worth a quick smoke-test** (e.g., `cargo publish --dry-run`, or checking a recently-published AGPL-3.0-or-later crate on crates.io) before relying on it working cleanly; I did not find independent 2026 confirmation that AGPL-3.0-or-later publishes cleanly today, only that the SPDX string itself (as opposed to `AGPL-3.0`) is the correct, current form. On the npm side, no AGPL-specific registry-level blocker was found — the only concern is likewise using the correct current SPDX identifier in `package.json`'s `license` field rather than the deprecated bare form. Sources: [rust-lang/crates.io#1278](https://github.com/rust-lang/crates.io/issues/1278), [rust-lang/crates.io#1435](https://github.com/rust-lang/crates.io/issues/1435), [SPDX AGPL-3.0 deprecation discussion](https://github.com/trufflesecurity/trufflehog/issues/1446).
