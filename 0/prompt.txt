## Cross-spec claim: partially accurate, and it under-counts

The claim lives in `michi-truncate.json`'s **`scope`** field (not on AC-004 itself, though it cites AC-004): *"The exact suffix format string ' ({N} chars truncated — use {hint})' pinned by AC-004 is duplicated verbatim as a golden value in .claude/specs/michi-toon.json (AC-043, AC-044, AC-012a, AC-012b), which hardcodes hint=\"full=true\" via render_toon()."*

Checking each half against the spec as read from disk:

- All four criterion IDs **exist**.
- **AC-043 — accurate.** Duplicates the format verbatim and additionally pins U+2014 and the literal `full=true`.
- **AC-012a — accurate.** Carries the fully-instantiated golden ` (500 chars truncated — use full=true)`.
- **AC-044 — inaccurate as stated.** It contains no suffix string; it references *"the Unicode scalar count of the suffix text (per AC-043)"*. It is suffix-*dependent* (its arithmetic breaks if the suffix length changes) but is not a duplication.
- **AC-012b — inaccurate, and misleading in a way that matters.** Its only occurrence of the string is the **negative** substring `" chars truncated"`, asserting *absence* of truncation for a 150-char cell. A suffix-format change would not fail AC-012b — it would silently weaken it into a vacuous assertion. It is the one criterion of the four that the pairing rule buys nothing for.
- **"hardcodes hint=\"full=true\" via render_toon()" — accurate.** `crates/michi-toon/src/render.rs:177`:
  ```rust
  let truncated = michi_truncate::truncate_inline(s, max_cell_len, "full=true");
  ```
  (Minor: the call is to `truncate_inline`, `crates/michi-truncate/src/lib.rs:92`, which delegates to `truncate`; the `format!` is at `lib.rs:55`.)

**The coupled set is larger than the claim says.** Also carrying the golden value, and unlisted: **AC-011** (verbatim ` (500 chars truncated — use full=true)` in its worked example), **AC-011c** and **AC-025a** (both pin ` (50 chars`, the hard-capped first 10 chars of the suffix — a change to the suffix's *leading* characters breaks them), and **AC-011b** (its 202-char/528-byte measurement is arithmetically derived from the 38-char suffix). The real pairing set is 7 criteria, not 4. If the pairing rule is to be relied on, `michi-truncate.json`'s scope note needs correcting to `AC-011, AC-011b, AC-011c, AC-012a, AC-025a, AC-043, AC-044` — and AC-012b dropped.

## Confounded witnesses and spec defects worth flagging

1. **AC-011b's stated purpose is itself confounded.** It claims to demonstrate *"that max_cell_len bounds Unicode scalar values (chars), not bytes."* But the render entry gate is **bytes** — `crates/michi-toon/src/render.rs:174` reads `if s.len() &lt;= max_cell_len`, and `CompactString::len()` is byte length. AC-011b's witness (300×日 = 300 chars / 900 bytes) exceeds the threshold on *both* measures, so it cannot discriminate the gate. Char semantics survive only because `michi_truncate::truncate` re-checks `char_count &lt;= max_chars` at `crates/michi-truncate/src/lib.rs:45-53` and returns unchanged. I verified the discriminating witness the spec lacks — 100×日 (100 chars / 300 bytes) at `max_cell_len=200` — and it renders **unmodified**, so there is no observable divergence today.

   The structural hazard: `michi-toon.json`'s `non_goals[1]` explicitly declares `truncate_inline`'s internals out of scope, yet AC-011/AC-011b/AC-043's char semantics depend on exactly that internal re-check. Remove it and `render_toon` becomes byte-bounded with no michi-toon criterion failing.
