- `ErrorCode::is_retryable_by_default()` / `DomainError.retryable` override — both directions tested (default-from-code, explicit override).

- `Sensitive<T>` redacts both `Debug` and `Display`.

- `hints::append_hints`/`render_hints`: empty slice → no-op/empty string (tested both as standalone fn and as in-place append), 1 vs 2 hints, `Hint::from(&str)`/`From<String>`.
- `recovery::render_recovery`: no params/no reason (bare tool name), params only, reason only, params+reason combined (exact byte-for-byte format), multiple hints count in header, empty → empty string, `Int`/`Bool`/`Float` param rendering, float-precision parity between `recovery` and `kv` render paths.
- `status::StatusResponse::render()`: tool/description always lead; `Health::Ok`/`None` → no bracket annotation; `Degraded`/`Error` → bracket annotation with reason; full multi-item example matches an exact expected string including column padding.

## (b) Handled in code but NOT tested
- **`DomainError.message` / `Hint` / `RecoveryHint.tool` / `RecoveryHint.reason` containing embedded newlines.** `DomainError::render()` and `hints::append_hints` push these fields verbatim with no escaping. A message or hint with `\n` will silently inject extra lines into the `error:`/`message:`/`help[N]:` block, breaking the fixed-line-count KV format an agent parser would assume. Not tested anywhere, and — unlike TOON's CSV-style values — nothing in this code path escapes or strips it.
- **`empty_state(type_name)` with a `type_name` containing `[`, `]`, `:`, or newlines.** Pushed verbatim into `"{type_name}[0]{{}}:\ntotalCount: 0\n"`; a name like `"issue]{evil}"` would corrupt the bracket/brace structure. No validation, no test.
- **`StatusItem.key` / `StatusResponse.tool_name`/`.description` containing newlines or colons.** Flows through `kv::render_kv`, which also does zero escaping on keys — same class of risk as above, untested for either module.
- **Whitespace-only strings** (message = `"   "`, hint = `"\t"`, tool_name = `""`) — not distinguished from meaningful values anywhere; renders as-is. No explicit test of this boundary, though behavior is at least well-defined (renders the literal whitespace).
- **`RecoveryHint.tool` containing a colon or the literal `" — "` separator** used between params and reason — could visually merge with the reason text. Untested.
- **`FailedOp.operation` containing a comma or newline** in `PartialSuccess::render()`'s `failed[N]{operation,reason}:` block — `operation` is pushed raw (unlike `reason`, which goes through `crate::toon::escape_value_quoted`). A comma in `operation` would silently shift the CSV-like column split for any naive parser. Same for `completed`/`skipped` entries — pushed raw, no escaping, untested with delimiter-bearing strings.
- **`escape_value_quoted` strips (not escapes) `\n`/`\r`** — confirmed by its own unit test (`"line\nbreak"` → `"linebreak"`, words silently concatenated). This is exercised directly in `src/toon/escape.rs` but never through `PartialSuccess::render()`'s actual call site, so the *combined* behavior (a failed-op reason with a newline, rendered end-to-end) is untested.
- **Very large hint counts / very long single hint strings** — no test near any capacity-estimate boundary (`String::with_capacity` calls use heuristics; under-sizing just causes a realloc, not a correctness bug, but no test confirms no truncation/panic at scale).
- **`RecoveryHint.params` with duplicate keys** — e.g. two `("user", ...)` params — renders both in order with no dedup; not asserted anywhere as either "supported" or "invalid."
- **No snapshot-test coverage at all** for `error`, `hints`, `recovery`, or `idempotency` modules — `tests/snapshot_tests.rs` only covers `empty`, `kv`, `status`, `toon`, `response`. Any accidental formatting regression in `DomainError::render()`, `render_recovery()`, or `PartialSuccess::render()` would only be caught by the module's own inline `assert_eq!` tests, not insta snapshots — lower review visibility for output-format drift (e.g. someone changing a separator string wouldn't get a diff).

## (c) Not handled at all — gaps/bugs
- **No integration path from `DomainError`/`Error` into `mcp::CallToolResult`.** `response.rs`/`mcp.rs` never reference `DomainError`, `ErrorCode`, or `error::Error` (confirmed via grep — zero hits). There's no `AgentResponse`/`to_call_tool_result()`-style helper that turns a `DomainError` into a `CallToolResult` with `is_error: true` — a caller must hand-build that themselves from `DomainError::render()`, duplicating the wiring `AgentResponse` already does for success paths. **Severity: Medium** — not a bug per se (may be deliberate per the "M":"data/render type" decision in 06-decisions.md), but it's a real coverage hole for anyone expecting michi to own the full error→MCP-response path, and there's no test proving the intended caller-side wiring actually produces valid `isError:true` output.
- **No validation/rejection of empty `ErrorCode`-independent inputs anywhere in this cluster.** Every `impl Into<String>` constructor (`DomainError::new`, `Hint::new`, `RecoveryHint::new`, `empty_state`, `StatusResponse::new`, `IdempotencyKey::new`) accepts empty strings unconditionally and renders them as empty fields rather than, say, omitting the field or erroring. This is likely intentional ("michi doesn't validate business rules") but there's no doc comment or test asserting it's a deliberate non-goal — a future contributor could "fix" this inconsistently across just some of the six modules. **Severity: Low.**
- **`AlreadyDone` vs `PartialSuccess` boundary is a documentation/API-clarity gap, not a bug**: nothing in the code stops a caller from calling `render_already_done()` for an operation that actually partially failed, or `PartialSuccess::render()` for one that's fully done. The two are structurally independent (per `06-decisions.md`'s "check split from render" note) with no shared discriminant type or invariant enforced by the type system — a caller mixing them up (e.g., reporting `already_done` when some sub-steps actually failed) would produce a confidently wrong response with no way for michi to catch it. **Severity: Low-Medium** — inherent to the "michi owns no persistence" design, but worth flagging since it's the exact ambiguity the prompt asked about and nothing in the module guards against caller misuse.
- **`ErrorClass::Internal` is unreachable in practice.** `ErrorClass` has three variants (`User`, `Internal`, `Transient`) but `Error::class()`'s match arm never produces `Internal` — only `User` and `Transient` are returned (confirmed in `src/error.rs:231-236`, mirrored in `crates/michi-core`). No test exercises `Internal`, and no code path constructs it. Either it's dead code reserved for a future `Error` variant (plausible given `#[non_exhaustive]` and the pipeline-crate note in `06-decisions.md`), or it's a latent classification gap where an internal/infra `DomainError` today gets classified as `User` regardless of code. **Severity: Medium** — worth confirming intent; if `Internal` is meant to be reachable today, this is a real classification bug, not just missing coverage.
