### Issue 1 — Missing error case: `validate()` also enforces name checks, not just row length

**Affects**: `scope` (the `render_toon` fix description), `AC-004`, `AC-008`. Type: `missing-error-case` (with an `ambiguous` component in AC-004/AC-008's wording).

**Problem**: `ToonOptions::validate()` (`crates/michi-toon/src/lib.rs:130-152`) performs three checks, not one:
1. `InvalidTypeName` — `type_name` contains a structural character (`[`, `]`, `{`, `}`, `,`, `\n`, `\r`)
2. `InvalidFieldName` — any field name contains a structural character
3. `RowLengthMismatch` — a row's length doesn't equal `fields.len()`

The spec's purpose and scope frame this fix entirely in terms of check #3 ("row/field validation" is used loosely to mean row-length checking). But the scope directs calling `validate()` unconditionally, which wires in checks #1 and #2 as a side effect.

Today, without `validate()`, `render_toon` doesn't reject structural characters in `type_name`/field names — it silently sanitizes them. Confirmed at `crates/michi-toon/src/escape.rs:77-79` (`sanitize_header_token`): any of `[`, `]`, `{`, `}`, `,`, `\n`, `\r` in a header token is replaced with `_`, and rendering succeeds.

**Concrete failure scenario**: `renderToon({ typeName: 'a[b]', fields: ['x'], rows: [['v']] })`.
- Before the fix: succeeds, renders with `typeName` sanitized to `a_b`.
- After the fix (per scope, `validate()` called unconditionally): throws a new `napi::Error` for `InvalidTypeName` — behavior that previously succeeded now fails.

This directly conflicts with two existing criteria:
- **AC-004** says: "Calling renderToon with valid input where every row length equals fields.length continues to succeed with no new rejection." — "valid input" is undefined with respect to type_name/field-name content, so this criterion is ambiguous about whether `a[b]` counts as "valid," and as literally read it's simply false post-fix.
- **AC-008** says: "Existing Node test suite and insta snapshots produce the same pass/fail outcome after the fix for every pre-existing case." — if any existing test (or any future caller) passes a structural character in `type_name`/fields, this guarantee breaks.

No acceptance criterion in the spec exercises the new `InvalidTypeName`/`InvalidFieldName` rejection at all.

**Suggested fix**:

&gt; `toon_opts.validate()` also enforces `ToonError::InvalidTypeName` and `ToonError::InvalidFieldName`.
