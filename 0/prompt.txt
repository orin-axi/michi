## Issue 1 — lower-bound assertion (tests/proptest_resilience.rs)

Read `next_retry_delay` in src/resilience/mod.rs closely before asserting anything. The true lower bound is NOT flatly `base_delay` — it's `min(base_delay * 2^attempt, max_delay)`:

- `jitter_ms = (raw_ms as f64 * jitter_factor * jitter_seed) as u64` where both factors are in [0.0, 1.0] → jitter is always ≥ 0, so `jittered_ms = raw_ms + jitter_ms ≥ raw_ms` (jitter only ever raises the delay, confirming the reviewer's premise).
- `retry_after` is `None` in this test, so `max(jittered_ms, retry_after_ms) = jittered_ms`.
- Final: `capped_ms = min(jittered_ms, max_ms) ≥ min(raw_ms, max_ms)` — provable case-by-case (whether `raw_ms ≤ max_ms` or not, `min(X, max_ms) ≥ min(raw_ms, max_ms)` holds whenever `X ≥ raw_ms`).

This matters concretely under the test's own generator ranges: `attempt` up to 4 and `base_secs` up to 9 means raw backoff can be up to 9×16=144s, while `max_secs` tops out at 59s — so the cap-before-jitter case is *regularly* exercised, not a corner case. A flat `>= base_delay` assertion would've been correct but weaker/misleading about what's actually being verified.

Renamed the test `next_retry_delay_within_max_delay_bound` → `next_retry_delay_within_bounds` and added:
```rust
let exp = 2u32.saturating_pow(attempt);
let raw_backoff = config.base_delay.saturating_mul(exp);
let expected_min = raw_backoff.min(config.max_delay);
prop_assert!(delay >= expected_min, ...);
```
